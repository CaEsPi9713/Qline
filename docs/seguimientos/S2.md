#### TT-007 · Contador y cola · [`app/cola.py`](../../app/cola.py)

| Estructura | Clave | Operaciones |
|---|---|---|
| String | `grupo2:qline:contador:atencion_general` | `INCR` para generar `A-001`, `A-002`, etc. |
| Sorted Set | `grupo2:qline:cola:atencion_general` | `ZADD NX`, `ZRANGE`, `ZPOPMIN` |
| String | `grupo2:qline:ventanilla:{id}:actual` | Turno asignado a cada ventanilla |

**Orden de la cola.** `score = nivel * 10^13 + llegada_ms`, con nivel 0 para preferencial y 1 para normal. La prioridad siempre domina a la hora de llegada y, a igual prioridad, se conserva FIFO. Los valores caben exactos en un double.

**Decisiones de diseño:**
- `ZADD NX` hace que reencolar un código ya presente no lo duplique ni lo reordene.
- La extracción usa `ZPOPMIN`, que es atómico: dos ventanillas simultáneas nunca reciben el mismo miembro.
- Consultar la cola usa solo `ZRANGE`, que no remueve nada.
- Ventanillas y prioridades inválidas se rechazan con un error controlado.
- No se usa `FLUSHALL` ni `FLUSHDB`.

#### HU-004 · Vista de cola
- `GET /cola`: tabla con posición, código y prioridad y el conteo de turnos en espera. `GET /api/cola` devuelve lo mismo en JSON.
- Si Redis no responde, la página muestra un error controlado y la API responde 503.

#### HU-005 · Llamar siguiente · [`app/llamado.py`](../../app/llamado.py)
Redis decide el turno y MongoDB registra el cambio:

1. `ZPOPMIN` extrae el siguiente turno de forma atómica y lo guarda como actual de la ventanilla.
2. En MongoDB, `find_one_and_update` con filtro `estado == "pendiente"` establece `estado = llamado`, `ventanilla` y `timestamps.llamado`.
3. Se calcula `metricas.espera_seg` a partir de `timestamps.creado`.

| Situación | Respuesta |
|---|---|
| Cola vacía | `ok`, con `codigo: null` y un mensaje. |
| Ventanilla inválida | 400. |
| MongoDB falla después de extraer | 503. El turno vuelve a la cola con su score original, sin perderse ni dejar estados parciales. |
| Turno en Redis que no está `pendiente` en MongoDB | 409. Se descarta de la cola y se libera la ventanilla. |

Interfaces: `POST /api/llamar` (JSON) y el botón **Llamar siguiente** de `/cola`, con selector de ventanilla.

#### Rediseño de la interfaz y guía de demo · [`static/style.css`](../../static/style.css), [`base.html`](../../app/templates/base.html), [`demo.html`](../../app/templates/demo.html)

### Qué se implementó

#### HU-001 · Emitir turno · [`app/emitir.py`](../../app/emitir.py)
1. Valida la prioridad (`normal` o `preferencial`).
2. Obtiene un código único con el contador atómico de Redis (`cola.siguiente_codigo()`).
3. Persiste el documento inicial en MongoDB (estado `pendiente`, `timestamps.creado` en UTC, el resto de los tiempos en `null`).
4. Encola el turno en la cola de Redis (`cola.encolar()`), respetando prioridad y llegada.

**Fallos parciales** (para no dejar duplicados ni estados ocultos):
- Si el encolado se rechaza de forma confirmada, se compensa eliminando únicamente el documento que acaba de insertarse.
- Si la falla es ambigua (timeout o desconexión), el documento se conserva para reconciliarlo después, porque el turno pudo haber llegado a Redis.
- Los mensajes de error no exponen credenciales ni detalles internos.

Interfaces: `POST /api/turnos/emitir` (JSON o formulario) y el formulario web `/emitir`, que lleva a una pantalla de confirmación con el ticket del turno ([`emitir.html`](../../app/templates/emitir.html) y [`turno_confirmado.html`](../../app/templates/turno_confirmado.html)).

#### HU-002 · Consultar turno · [`app/consultar.py`](../../app/consultar.py)
- Solo lectura: no modifica MongoDB ni Redis.
- MongoDB determina el estado y Redis solo aporta la posición de los turnos pendientes. Si Redis falla, el estado del turno se muestra igual, con un aviso.
- Código con formato inválido: respuesta controlada (400). Código inexistente: 404. Estado desconocido: 409. MongoDB caído: 503.
- Interfaces: `GET /api/turnos/{codigo}` (JSON), `GET /consultar` (buscador) y `GET /turno/{codigo}` (enlace directo, base para el QR de S3).

- `finalizar_atencion`: `en_atencion` pasa a `atendido`, registra `timestamps.finalizado` y `metricas.atencion_seg`.
- **Concurrencia:** el estado se comprueba y se cambia en una sola operación `update_one` con filtro. Si dos solicitudes actúan sobre el mismo turno a la vez, solo una lo modifica; un reintento no sobrescribe los tiempos ya registrados.
- **Errores controlados**, sin respuestas 500:

| Caso | Código |
|---|---|
| Turno inexistente | 404 |
| Estado inválido para la acción, o ventanilla distinta a la que llamó | 409 |
| Código o ventanilla inválidos | 422 |
| Turno `en_atencion` sin inicio registrado | 409 |
| MongoDB no disponible | 503 |

- Rutas `POST /api/atencion/iniciar` y `POST /api/atencion/finalizar`; las fechas se devuelven en UTC con `Z`. Excepciones en [`app/excepciones.py`](../../app/excepciones.py) y modelos de respuesta en [`app/schemas.py`](../../app/schemas.py).

#### Consistencia con Redis · [`app/redis_atencion.py`](../../app/redis_atencion.py)
Al finalizar, el turno deja de ser el actual de su ventanilla y se retira de la cola de Redis (`ZREM`). La clave `ventanilla:{id}:actual` solo se borra si todavía apunta a ese turno. Si Redis falla después de que MongoDB registró la finalización, el turno queda `atendido` y la respuesta indica `redis_liberado: false`. Solo se tocan claves `grupo2:qline:`.

#### Panel de atención · [`app/panel_atencion.py`](../../app/panel_atencion.py) y [`panel.html`](../../app/templates/panel.html)
- `GET /panel`: tarjeta por ventanilla (V-01, V-02 y V-03) con el turno actual, su estado y su prioridad, y el botón **Iniciar atención** o **Finalizar atención** según corresponda, con mensajes de éxito y de error.
- El turno actual se lee de Redis; si Redis no responde o no lo tiene, se busca en MongoDB un turno de esa ventanilla `en_atencion` o `llamado`. Si Redis apunta a un turno ya terminado, se ignora y se avisa.
- Separado del CRUD administrativo y de la vista de cola.

#### TT-005 · Datos sintéticos · [`scripts/sinteticos/`](../../scripts/sinteticos)
- [`generar_datos_sinteticos.py`](../../scripts/generar_datos_sinteticos.py) simula la fila (prioridad antes que llegada, FIFO, 3 ventanillas, abandono a los 180 s) y genera turnos coherentes con el contrato. Valida el conjunto antes de escribir.

- Carga con upsert por `codigo` (no duplica). `--limpiar` y `--reiniciar` exigen `--confirmar` y solo afectan a la serie `S-`.
- Documentado en la sección 2 del README. [`sembrar_turnos_hu006.py`](../../scripts/sembrar_turnos_hu006.py) siembra `A-015` a `A-020` para probar HU-006 y HU-007.
